# Desktop calibration architecture

**Status:** foundation implemented and tested with synthetic data only (2026-10-31). Nothing in
this document has been measured on the cameras yet; see
[calibration-validation-guide.md](../testing/calibration-validation-guide.md).

## Assessment of the starting point

What existed (`main` at 617a250):

* `software/diagnostic/` (`sight-diag`, Python 3.10+, OpenCV 5 contrib, uv): capture once per
  camera into a newest-frame `FrameSlot`, independent processor threads with exception
  isolation (`quality`, `face` = YuNet, `eyes` = YuNet landmarks + dark-pupil finder,
  `landmarks` = optional MediaPipe 478-point mesh with iris and uncalibrated head pose), a
  synthetic and a replay source, a recorder, and an experimental 3×3 screen-target calibration
  (`calibration.py`: second-order polynomial on pupil offsets, leave-one-out RMS).
* `docs/architecture/shared-interface.md`: camera IDs, rig frame (X right, Y up, Z toward the
  user, mm/deg), experiment config.
* No desktop application, no display model, no profile, no protocol between processes.

Reused directly: the capture/processing pipeline and its isolation, the synthetic source and the
experiment config (the engine's camera mode opens a `sight-diag` config), the MediaPipe and YuNet
processors, `calibration.poly_features` (the one polynomial definition), `calibration.grid_targets`,
`mean_offset`, the leave-one-out idea, and the rig-frame conventions.

Risks and inconsistencies found:

| Finding | Consequence / handling |
|---|---|
| The pupil offset (`eyes`) is relative to a YuNet *eye-centre* landmark that itself moves with gaze. | Weak gaze signal. The new `iris-in-eye/v1` feature uses the MediaPipe eye corners as the reference; the YuNet offset is the fallback. |
| MediaPipe's head pose is uncalibrated and its RGB training on near-infrared monochrome images is unverified. | Pose values are labelled uncalibrated everywhere; the baseline records which features were valid. |
| The diagnostic tops out at ~68 fps (MJPEG decode to colour then grey on the capture thread, measured 2026-10-31). | Not changed here (the user has not decided on the proposed fix). Calibration works at any rate; the engine reports the measured fps. |
| Both cameras report the same USB serial (UC762). | Profiles bind cameras by `/dev/v4l/by-path`, as the diagnostic does. |
| The leave-one-out RMS was the only quality number. | Kept as a *training* diagnostic and labelled as such; accuracy comes only from independent validation targets. |
| `shared-interface.md` still describes the superseded adjustable rig (baseline 70–160 mm). | The profile stores the measured baseline (fixed rig, ~257 mm). The interface doc should be updated by the mount thread. |
| Wayland restricts global cursor reads and input injection. | Calibration never needs the cursor; pointer output is a dry run. |

## Ownership

| Part | Language | Owns |
|---|---|---|
| [`contracts/`](../../contracts/README.md) generated from `software/desktop/crates/contracts` | Rust types → JSON Schema + TypeScript | every stored or exchanged structure and its version |
| `software/desktop/crates/geometry` | Rust | display model, discovery (sysfs EDID, X11 RandR), every coordinate transform, metric scale |
| `software/desktop/crates/profile` | Rust | profile store: atomic writes, schema validation, migration, model history |
| `software/desktop/crates/session` | Rust | engine process client, clock mapping, workflow state machines, model acceptance, compatibility, dry-run pointer; `sight-calibrate` headless CLI |
| `software/desktop/app/src-tauri` | Rust (Tauri 2) | desktop shell: commands and window control only |
| `software/desktop/app/src` | Svelte 5 + TypeScript | calibration wizard, target presenter, diagnostics views |
| `software/diagnostic` (`lynx_sight_diag`) | Python | capture, features, face baseline, target plans, sample filtering, timing alignment, gaze-model fitting, validation metrics, synthetic observer; `sight-engine` (stdio) and `sight-diag` (standalone) |

Single source of truth, concretely:

* Polynomial features: `lynx_sight_diag.calibration.poly_features`, used by the legacy fit and
  the new model.
* Target positions and trajectories: generated by the engine (`calibration/targets.py`); the UI
  only interpolates the sampled path and reports what it drew.
* Coordinate transforms: Rust geometry only. The engine receives a precomputed `MetricScale`
  (pixel size, physical size, eye position in the display frame) and does no frame transforms.
* Accuracy and model comparison: the engine computes them; the core enforces the policy that a
  model never replaces a better one silently.
* Compatibility of a profile with current conditions: the core (`session/compatibility.rs`), from
  typed tracking status and the profile.

## Processes and data flow

```
 Svelte UI ── Tauri commands ──► desktop core (Rust) ── JSON lines (stdin/stdout) ──► sight-engine (Python)
   presenter: draws targets,       workflow state,           protocol v1                capture ─► features ─► buffer
   reports drawn frames            profile store,                                      plans, alignment, fit,
   (performance.now)               geometry, clock map                                 validation, synthetic user
```

* Time: every timestamp that crosses a boundary is CLOCK_MONOTONIC nanoseconds, the clock of
  V4L2 buffer timestamps, Python's `time.monotonic_ns()` and `rustix::time::clock_gettime`. The UI
  measures with `performance.now()`; the core maps it with an offset measured at clock sync and
  records the uncertainty. Display latency (draw call to photons) is not measured; pursuit
  alignment estimates the whole presentation-to-feature lag instead of assuming it.
* Synthetic mode: the engine's synthetic source is a deterministic simulated user (seeded) that
  looks at what the presenter reports with lag, noise, blinks, eye loss, head motion, lapses,
  offsets and drift. It exercises every workflow without cameras; it says nothing about real
  accuracy.

## Workflows

* **Full:** source → readiness → face baseline (stable, neutral, pose range) → stationary fit
  targets → pursuit fit path → independent validation targets → fit → review → accept.
* **Quick:** compatible profile → a few stationary targets + a few validation targets → engine fits
  a regularised affine correction on the current model → compares both on the same fresh
  validation data → accepted only if better; the previous record stays in history.
* **Incremental (interface only):** trusted observations (explicit confirmation or validation
  targets, never arbitrary clicks) → bounded offset proposal → same comparison gate. Not wired
  to any automatic trigger.

## Deliberate limits of this foundation

* Gaze model: second-order polynomial of combined iris-in-eye features plus linear head-position
  terms. No 3-D eye model, no stereo triangulation (needs the stereo calibration of the test
  plan first).
* Millimetre and degree errors are reported only when the display size and screen pose are
  known; until then they are `unavailable` with the reason.
* No real pointer injection. The pointer-intent contract and a dry-run backend exist; a host
  backend (uinput or a Tower link) is future work, see
  [pointer-integration.md](pointer-integration.md).
